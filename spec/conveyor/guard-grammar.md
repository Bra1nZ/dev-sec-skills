# Грамматика гвардов для L2

> **Статус:** спецификация `open`. Реализации экстрактора нет, пилота нет, ни
> один гвард по этой грамматике не извлечён и не проверен. Документ фиксирует,
> что L2 **может** и, что важнее, **не может** проверять. Английская версия —
> производная: [`guard-grammar.en.md`](guard-grammar.en.md). Единственный
> реализованный механизм — супервизия bounded-прогона (§6.6); она не делает
> реализованной саму грамматику.
>
> **Нормативные слова.** `MUST`, `MUST NOT`, `SHOULD` — по RFC 2119/8174.
> Всё, что помечено `open`, не является механизмом, пока не появится evidence.

## 1. Зачем эта грамматика

L2 регенерирует срез формальной модели из неаннотированного кода и проверяет
инварианты на этом срезе. Чтобы регенерация была возможна, множество
выразимых охранных условий (гвардов) должно быть **ограничено**: бесконечный
язык нельзя ни извлечь надёжно, ни проверить за минуты.

Грамматика решает три задачи:

1. **Вход экстрактора.** Что считать гвардом, а что — корзиной `unroutable`.
2. **Вход транслятора.** Как гвард становится предикатом модели.
3. **Граница обещания.** Какие ячейки L2 закрывает, а какие — нет.

Грамматика **не** является языком программирования, DSL для разработчиков или
форматом аннотаций в коде. Код остаётся неаннотированным; гварды извлекаются.

## 2. Скоуп

### 2.1 Что покрывается

- Ролевой и уровневый доступ (RBAC/ABAC-срез).
- Объектная авторизация: сравнение атрибутов субъекта и объекта.
- Проверка существования атрибута или связи.
- Срок жизни учётных данных (TTL) и возраст ресурса.
- Композиция этих предикатов через `and`, `or`, `not`.

### 2.2 Что не покрывается (и обязано попадать в `unroutable`)

- Конкурентность: блокировки, гонки, check-then-act, fencing tokens.
- Транзакции и частичная запись, откат, идемпотентность.
- Криптография, подписи, сравнение секретов.
- Сеть, ретраи, таймауты, доставка сообщений.
- Supply chain, сборка, зависимости.
- Память, очистка буферов, утечки через логи.
- Производительность и UX.
- Любая логика, зависящая от значения, полученного вне объявленного контекста
  (см. 7.4).

Граница проходит не по «сложности», а по **наблюдаемости**: если условие
нельзя выразить предикатом над объявленным контекстом события, экстрактор не
имеет права угадывать.

## 3. Термины

| Термин | Значение |
| --- | --- |
| **Событие** (`event`) | точка принятия охранного решения: `db.invoices.select`, `http.invoices.update`, `job.payout.run` |
| **Контекст** (`context`) | типизированное описание величин, доступных на событии: субъект, ресурс, учётные данные, время |
| **Гвард** (`guard`) | именованное условие, разрешающее событие; всё остальное запрещено |
| **Действие** (`action`) | что происходит при отказе: `deny`, `abort`, `rollback`, `safe-degrade` |
| **Модель** | множество событий и гвардов, регенерированное из кода |
| **Срез** | модель, ограниченная изменёнными функциями и их достижимыми зависимостями |

## 4. Грамматика

### 4.1 Файл

```ebnf
guard_file   = { declaration } ;
declaration  = context_decl | guard_decl ;

context_decl = "context" ident "{" { field } "}" ;
field        = path ":" type { modifier } ";" ;
type         = "bool" | "int" | "string" | "uuid" | "timestamp"
             | "enum" "{" ident { "," ident } "}"
             | "set" "<" type ">" ;
modifier     = "optional" | "derived" ;

guard_decl   = "guard" ident "on" event ":"
               expr
               "otherwise" action ";" ;
event        = ident { "." ident } ;
action       = "deny" | "abort" | "rollback" | "safe-degrade" ;
```

### 4.2 Выражения

```ebnf
expr         = disjunction ;
disjunction  = conjunction { "or" conjunction } ;
conjunction  = negation { "and" negation } ;
negation     = [ "not" ] primary ;
primary      = "(" expr ")" | predicate ;

predicate    = membership | comparison | existence | age | constant ;
membership   = path "in" "{" value { "," value } "}" ;
comparison   = path cmp value ;
existence    = "exists" "(" path ")" ;
age          = "age" "(" path ")" cmp duration ;
constant     = "true" | "false" ;
cmp          = "==" | "!=" | "<" | "<=" | ">" | ">=" ;

path         = "$" ident { "." ident } ;
value        = literal | path ;
literal      = string | number | boolean | "null" ;
duration     = number ( "s" | "m" | "h" | "d" ) ;
```

### 4.3 Лексика

- `ident` — `[A-Za-z_][A-Za-z0-9_]*`.
- `string` — в двойных кавычках, без интерполяции.
- `number` — целое или десятичное; отрицательные числа допускаются только в
  литералах, но не в путях.
- Комментарии `//` до конца строки. Комментарии не являются частью модели.
- Никаких пользовательских функций, макросов, регулярных выражений,
  арифметики и вызовов. `age(...)` — единственная встроенная функция.

### 4.4 Пример

```text
context Request {
  $subject.tenant_id   : uuid;
  $subject.role        : enum {reader, writer, admin};
  $subject.level       : int;
  $resource.tenant_id  : uuid;
  $resource.status     : enum {draft, issued, paid, void};
  $credential.issued_at: timestamp;
}

guard invoice_read on db.invoices.select:
  $resource.tenant_id == $subject.tenant_id
  and $subject.role in {reader, admin}
  and $resource.status != void
otherwise deny;

guard invoice_write on db.invoices.update:
  $resource.tenant_id == $subject.tenant_id
  and $subject.role in {writer, admin}
  and $subject.level >= 2
  and age($credential.issued_at) <= 24h
otherwise deny;
```

## 5. Семантика

### 5.1 Гвард — это allow-list

`guard g on e: E otherwise A` означает: событие `e` разрешено **только** если
`E` истинно. Если `E` ложно или не определено — выполняется `A`. Отсутствие
гварда для события означает запрет. Это и есть default deny, встроенный в
язык, а не соглашение.

### 5.2 Три значения

Вычисление тотально и трёхзначно: `true`, `false`, `unknown`.

| Ситуация | Результат |
| --- | --- |
| путь отсутствует в контексте и не помечен `optional` | `unknown` |
| `optional`-путь отсутствует | `unknown` |
| сравнение разных типов | `unknown` |
| сравнение с `null` через `<`, `<=`, `>`, `>=` | `unknown` |
| `age()` от отсутствующего или будущего (за пределами skew) времени | `unknown` |
| `exists()` | `true` или `false`, никогда `unknown` |
| `not unknown` | `unknown` |

Таблицы `and`/`or` — по Клини: `unknown and false = false`,
`unknown or true = true`, остальные комбинации с `unknown` дают `unknown`.

**Итог:** `unknown` в корне выражения означает отказ. Реализация MUST NOT
трактовать `unknown` как `true` и MUST NOT использовать короткое замыкание,
меняющее итог.

### 5.3 Ловушка отрицания

`not ($resource.tenant_id == $subject.tenant_id)` при отсутствующем
`tenant_id` даёт `unknown`, то есть отказ. Это правильно для allow-list, но
означает, что «запретить, если совпало» нельзя писать через отрицание
разрешения. Для запрета используется отдельный гвард с действием `deny` и
явным `exists()`; смешивать разрешение и запрет в одном выражении запрещено
(см. 5.5).

### 5.4 Несколько гвардов на событие

Если на одно событие извлечено несколько гвардов, они соединяются по
**deny-overrides**: событие разрешено, только если разрешают все. Один
либеральный гвард не может перекрыть строгий. Это защищает от ошибки, когда
экстрактор нашёл проверку в middleware и «забыл» объектную проверку в
обработчике.

### 5.5 Запрет смешения режимов

Гвард не может одновременно разрешать и запрещать. Действие `deny` при
истинном выражении не поддержано: для запрета вводится отдельное событие или
отдельный гвард с инвертированным смыслом и явным `exists()`. Это ограничение
сознательное: смешение режимов делает модель неоднозначной, а доказательство
— бессмысленным.

### 5.6 TTL

`age($path) <= D` требует доверенных часов. Источник времени, допустимый skew
и поведение при отсутствии метки объявляются в манифесте извлечения.
`age()` от будущей метки в пределах skew считается `0`; сверх skew —
`unknown`. TTL не доказывает отзыв: он проверяет только возраст метки.

### 5.7 Уровни

`$subject.level` — целое из объявленного домена. Сравнения `<`, `<=`, `>`,
`>=` допустимы только для `int` и `timestamp`. Уровни не упорядочивают роли:
`role` и `level` — независимые измерения, и требование «роль ИЛИ уровень»
выражается явно.

## 6. Контракт экстрактора

Экстрактор — TCB. Ошибка экстрактора, теряющая гвард, делает гейт проходимым
при дырявой модели. Поэтому контракт сформулирован как обязательства, а не как
пожелания.

### 6.1 Направление soundness

Модель обязана **над-аппроксимировать** поведение кода:

```text
E_code ⊆ E_model
∀ e ∈ E_code: Allowed_code(e) ⊆ Allowed_model(e)
```

В терминах гвардов: если код разрешает запрос, модель обязана его разрешить.
Модель может разрешать больше (это даёт ложные срабатывания, что безопасно) и
не может разрешать меньше (это скрывает реальную дыру). Обратное направление
— `Allowed_model ⊆ Allowed_code` — **запрещено**: оно превращает гейт в
фильтр ложных успокоений.

### 6.2 Три гейта

| Гейт | Условие прохождения | Провал |
| --- | --- | --- |
| **Полнота событий** | каждое security-событие изменённого кода есть в модели | merge закрыт |
| **Уточнение поведения** | для каждого события `Allowed_code ⊆ Allowed_model` | merge закрыт |
| **Невакуумность** | модель не пуста, каждый target не вырожден, есть достижимый путь отказа | merge закрыт |

Невакуумность проверяется явно:

- ноль событий в срезе — провал, а не «нечего проверять»;
- target, чей антецедент тривиально `false`, — провал;
- target, чей антецедент тривиально `true` и потому ничего не ограничивает, —
  провал;
- все события среза совпадают с одним шаблоном, а изменённая функция не
  дала ни одного события, — провал.

### 6.3 Манифест извлечения

Экстрактор обязан выдавать манифест:

```json
{
  "extractor": {"name": "...", "version": "...", "hash": "sha256:..."},
  "commit": "...",
  "context": {"clock": "...", "skew_seconds": 0},
  "events": [
    {"id": "db.invoices.select", "source": "path/to/file:120-138",
     "guard": "invoice_read", "action": "deny", "confidence": "exact"}
  ],
  "unroutable": [
    {"source": "path/to/file:140-149", "reason": "row-lock",
     "snippet_hash": "sha256:..."}
  ],
  "coverage": {"functions_changed": 0, "functions_extracted": 0}
}
```

`confidence: exact` означает, что гвард извлечён без домыслов. Любая другая
confidence — `unroutable`. Манифест хэшируется и входит в вердикт (C-13).

### 6.4 Мутационный набор

Экстрактор проверяется мутациями кода, а не только юнит-тестами. Минимальный
набор:

| ID | Мутация | Обязательный результат |
| --- | --- | --- |
| M1 | внести гвард в ранее открытую функцию | событие появилось, гвард извлечён |
| M2 | удалить гвард | событие изменилось или исчезло |
| M3 | заменить `==` на `!=` | предикат изменился |
| M4 | сузить набор ролей | предикат изменился |
| M5 | изменить TTL | предикат изменился |
| M6 | перенести проверку в middleware без изменения семантики | событие осталось, дубликата нет |
| M7 | спрятать гвард в динамический SQL или макрос | `unroutable`, не тихий пропуск |
| M8 | обернуть гвард в feature flag | `unroutable` |
| M9 | продублировать гвард | одно событие, не два |
| M10 | удалить обработчик целиком | событие исчезло, маршрутизация изменилась |

Порог: **ноль тихих пропусков на M1–M5**. Для M7–M8 обязателен `unroutable`;
тихий пропуск — провал релиза экстрактора. M6, M9, M10 — регрессии
маршрутизации, а не soundness.

### 6.5 Версионирование

Изменение грамматики — reviewed change. Оно требует:

1. пересчёта мутационного набора;
2. повторного прогона на пилоте;
3. записи в реестре утверждений: что стало выразимо, что перестало.

Расширение грамматики без новой evidence запрещено: иначе граница обещания
двигается молча.

### 6.6 Bounded fallback: таймаут — это `unverified`

Проверка выживания целей и любая L2-проверка, запускающая внешний
инструмент, выполняется под wall-clock bound. Артефакт проверки (модель, лог,
обрезанный хвост) не отличает завершённый прогон от убитого; отличает только
запись о том, как прогон закончился. Поэтому запись `tool_output`
(`schemas/tool-output.schema.json`) обязана содержать `status` с одним из
четырёх значений:

| `status` | Когда | Что означает |
| --- | --- | --- |
| `completed` | процесс завершился до bound | инструмент сказал что-то; что именно — в логе |
| `unverified` | bound истёк и группа процессов убита, либо инструмент сам сообщил, что не смог решить | вывода нет; лог обрезан или пуст |
| `failed` | процесс завершился с non-zero до bound | прогон не состоялся; причина — в логе |
| `error` | супервизор не смог стартовать или наблюдать процесс | прогона не было |

Нормативные правила:

1. **Bound обязателен и записан.** `bound_seconds` — целое ≥ 1. Прогон без
   записанного bound не является evidence для `model-checked`: неизвестно,
   что успели исследовать.
2. **Таймаут даёт только `unverified`.** `timed_out: true` при любом другом
   `status` — противоречие, отвергаемое L1. По истечении bound убивается вся
   группа процессов: дочерние процессы проверяющего не должны пережить
   родителя.
3. **`unverified` не поддерживает non-open claim.** L2 отвергает
   `status != completed` для любого claim со статусом выше `open`. То же
   правило независимо срабатывает на `timed_out: true` — вывод не зависит от
   того, какому полю поверит читатель.
4. **`failed` и `error` — тоже не поддержка.** Non-zero exit и отказ
   супервизора не становятся «проверено» из-за наличия артефакта.
5. **`completed` не равно «доказано».** `completed` говорит лишь, что
   процесс завершился сам. `verdict` остаётся собственной строкой инструмента
   в логе; супервизор её не пересказывает. Для `model-checked` bound
   state space остаётся отдельным обязательным полем.
6. **Нулевой exit — не вердикт.** Инструмент, который напечатал «не удалось
   решить» и вышел с кодом 0, обязан быть записан как `unverified`; адаптер,
   который это скрывает, ломает контракт.
7. **Открытый claim может честно хранить `unverified`.** Неудачная попытка —
   evidence о состоянии работы; наказания за неё нет. Запрет касается только
   попытки выдать её за закрытый claim.
8. **Non-zero как вердикт — задача адаптера.** Если контракт инструмента
   говорит «exit 1 = контрпример», супервизор всё равно пишет `failed`;
   отображение «контрпример» в вердикт делает адаптер, который цитирует лог.
   Молча трактовать non-zero как `completed` запрещено.

Механизм: `tools/bounded_check.py` (новая сессия процесса, `killpg` по
таймауту, combined stdout/stderr без вставок супервизора), схема
`schemas/tool-output.schema.json`, проверки L1/L2 в `tools/claim_lint.py`,
кейсы `evals/bounded-check/` (10/10) и `evals/linter/cases/tool-output-*.yaml`.

Что этот раздел **не** покрывает: распределённые проверяющие с собственными
таймаутами узлов, чекпоинты и возобновление после bound, адаптивный бюджет
(увеличение bound по мере роста модели), стоимость доли таймаутов на PR
(V2-30). Всё это — открытые вопросы, а не следствия из §6.6.

## 7. Карта «грамматика ↔ ячейки»

Все ячейки — из [`cells.seed.yaml`](cells.seed.yaml).

| Ячейка | Покрытие | Что именно покрывается | Что остаётся |
| --- | --- | --- | --- |
| CELL-001 broken-access-control | **да** | ролевой и tenant-гвард на каждом событии | платформенный обход, superuser, DBA |
| CELL-002 object-level-authorization | **да** | сравнение атрибутов объекта и субъекта | связи через несколько таблиц вне среза |
| CELL-008 stale-credential | **частично** | TTL метки, возраст ресурса | реальный отзыв, кэши сессий |
| CELL-010 batch-bypass | **частично** | только если batch-путь вызывает тот же гвард | доказательство общего choke point |
| CELL-012 insecure-defaults | **частично** | default-deny, выраженный гвардом | сканирование артефактов и профилей |
| CELL-003 partial-write | **нет** | — | транзакции, побочные эффекты |
| CELL-004 non-idempotent-retry | **нет** | — | ключи идемпотентности, доставка |
| CELL-005 check-then-act | **нет** | — | блокировки, изоляция |
| CELL-006 stale-worker | **нет** | — | fencing tokens, эпохи |
| CELL-007 lifecycle-cleanup | **нет** | — | очистка, логи |
| CELL-009 error-contract | **нет** | — | формат ошибок, утечки |
| CELL-011 supply-chain | **нет** | — | сборка, зависимости |

Правило: **`нет` означает `unroutable`, а не «проверено L2»**. Если
конфигурация обещает покрытие ячейки через L2, а ячейка в этой таблице `нет`,
обещание ложно.

## 8. Классы `unroutable`

Корзина не является свалкой. Каждый класс имеет причину и владельца решения.

| Класс | Пример | Почему вне грамматики |
| --- | --- | --- |
| `row-lock` | `SELECT ... FOR UPDATE`, `SKIP LOCKED` | зависит от планировщика и изоляции |
| `check-then-act` | чтение, затем запись без блокировки | требует модели состояний и гонок |
| `dynamic-sql` | конкатенация условия в строку | условие не наблюдаемо статически |
| `macro-guard` | гвард внутри макроса или ORM-хука | граница раскрытия не определена |
| `external-policy` | решение вынесено в OPA/сервис | значения приходят вне контекста |
| `value-provenance` | tenant берётся из заголовка клиента | грамматика видит значение, не источник |
| `crypto` | сравнение подписи, `hmac.compare_digest` | не предикат над ролями |
| `time-window` | бизнес-окно, календарь | не TTL и не возраст |
| `numerical` | лимиты, квоты, балансы | требует арифметики |
| `feature-flag` | гвард включён флагом | модель зависит от конфигурации |
| `platform-bypass` | owner таблицы, `BYPASSRLS`, superuser | вне модели приложения |

Квота triage: пустая корзина — сигнал полноты на наблюдаемом потоке;
наполняющаяся — сигнал неизвестного неизвестного. Расширение таксономии
решают люди (CONCEPT.md, 5.3).

## 9. Пример: RLS на `invoices`

### 9.1 Код

```sql
CREATE TABLE invoices (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  status text NOT NULL,
  owner_id uuid NOT NULL
);

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;

CREATE POLICY invoice_read ON invoices
  FOR SELECT
  USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND status <> 'void'
  );

CREATE POLICY invoice_write ON invoices
  FOR UPDATE
  USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND current_setting('app.role') IN ('writer', 'admin')
  );
```

### 9.2 Модель

```text
context Request {
  $subject.tenant_id : uuid;
  $subject.role      : enum {reader, writer, admin};
  $resource.tenant_id: uuid;
  $resource.status   : enum {draft, issued, paid, void};
}

guard invoice_read on db.invoices.select:
  $resource.tenant_id == $subject.tenant_id
  and $resource.status != void
otherwise deny;

guard invoice_write on db.invoices.update:
  $resource.tenant_id == $subject.tenant_id
  and $subject.role in {writer, admin}
otherwise deny;
```

### 9.3 Что этот пример честно показывает

1. **`invoice_read` не проверяет роль.** Это не ошибка модели: политика
   действительно разрешает чтение любому субъекту своего тенанта. Если
   требование требует роли, дефект в политике, а не в экстракторе.
2. **`app.tenant_id` — `value-provenance`.** Грамматика видит сравнение, но не
   видит, что значение пришло из заголовка клиента. Это остаётся открытым:
   даже идеальная модель не докажет, что тенант нельзя подделать.
3. **`FOR UPDATE` — `row-lock`.** Блокировка не выражается и попадает в
   `unroutable`; конкурентность остаётся за L3 и нагрузочными тестами.
4. **Owner и `BYPASSRLS`** обходят политику. Это `platform-bypass` и
   обязательная строка scope в вердикте.
5. **`WITH CHECK` отсутствует.** Для `UPDATE` PostgreSQL использует `USING`
   и для новых строк, если `WITH CHECK` не задан; экстрактор обязан это
   знать, а не выводить «нет проверки» из отсутствия `WITH CHECK`. Это пример
   того, что экстрактор обязан быть специфичен для платформы.

### 9.4 Контрпример: проверка есть, но не та

```python
@app.get("/invoices/{invoice_id}")
@require_role("reader")
def get_invoice(invoice_id):
    return db.get_invoice(invoice_id)   # нет проверки tenant_id
```

Модель получит `http.invoices.read` с ролевым гвардом и **не** получит
объектного гварда. Гейт полноты событий пройден (событие есть), гейт
уточнения поведения — нет: `Allowed_code ⊄ Allowed_model` для объектной
ячейки, потому что код разрешает чужой `invoice_id`. Это ровно тот дефект,
который CELL-002 фиксирует как отдельную ячейку.

## 10. Отказные режимы самой спецификации

| Риск | Как проявляется | Мера |
| --- | --- | --- |
| Экстрактор как TCB | потеря гварда проходит молча | мутационный набор, 6.4 |
| Вакуумная модель | пустой срез «проходит» | vacuity check, 6.2 |
| Ложная точность | confidence `exact` без основания | `unroutable` по умолчанию |
| Дрейф платформы | PostgreSQL/ORM меняет семантику | платформенные тесты экстрактора |
| Подмена значения | tenant из заголовка | `value-provenance` в scope |
| Расширение языка ради покрытия | грамматика растёт без evidence | reviewed change, 6.5 |
| Ожидание «теорема на каждый PR» | синтез спецификации из кода выдают за проверку | L2 — model-diff и выживание целей, не синтез; доказательства перепрогоняются по изменению модели, кода, encoding или tooling (V2-29, `tools/proof_plan.py`) |

## 11. Открытые вопросы

1. Реализация экстрактора и его мутационного набора — фаза 2.
2. Пилот на реальной кодовой базе; без него все оценки стоимости L2 —
   гипотезы.
3. Формальная семантика трёхзначной логики в целевом верификаторе
   (`probcli`, Z3): как `unknown` кодируется в предикат.
4. Минимальный набор событий для не-SQL слоёв (HTTP-роутеры, gRPC, очереди).
5. Политика для `feature-flag`: считать конфигурацию частью кода или
   `unroutable`.
6. Связь вердикта L2 с реестром утверждений: какой claim закрывает покрытая
   ячейка.
7. Стоимость проверки выживания целей: доля таймаутов и бюджет
   синхронизации модели на PR. Политика `unverified` зафиксирована в 6.6;
   числа по-прежнему не измерены.

## 12. Что изменит этот документ

Спецификация перестанет быть `open`, когда:

- экстрактор пройдёт мутационный набор M1–M10 с нулём тихих пропусков;
- на пилоте измерены precision/recall извлечения против ручной разметки;
- vacuity-гейт сработал на внедрённой пустой модели;
- хотя бы одна ячейка из карты раздела 7 получила статус выше `open` с
  вердиктом и scope.

До этого документ — граница обещания, а не обещание.
