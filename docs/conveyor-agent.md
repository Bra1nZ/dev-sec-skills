# Конвейер модели: развёртывание и работа агента

Пошаговая инструкция для агента, который берёт этот репозиторий, разворачивает
конвейер у себя, прогоняет его на своём Rust-проекте и возвращает журнал и
метрики.

## Статус и границы

- **Статус:** V0 реализован в этом репозитории. Команды `make model-*`
  существуют, `make model-doctor` на встроенной фикстуре завершается с кодом 0.
  Прогон на вашем проекте начинается с него же: если doctor красный, конвейер
  ещё не развёрнут, и шаги ниже неприменимы.
- **Что проверяет `model-doctor`:** что Python, PyYAML, git и структура
  репозитория подходят; что все шаги проходят на `spec/fixtures/rust-tiny/` и
  дают ожидаемые числа — включая trait-метод без тела, на котором падал первый
  реальный прогон; что якоря разрешаются и не содержат исходного текста;
  что артефакты проходят свои JSON-схемы; что `handoff.json` валиден офлайн;
  что `bounds.yaml` без `rationale` отвергается, а валидный записывается как
  `declared: true, enumerated: false`; что крах вне ожидаемой ошибки
  журналируется событием, а `MODEL_OUT == <handoff>/artifacts` не роняет
  handoff; и что три гейта умеют падать — испорченный фрагмент делает `check`
  красным, снятый `no_guard_ok` валит `coverage`, папка без `JOURNAL.md`
  отвергается.
- **Чего `model-doctor` не проверяет:** что конвейер правильно понимает ваш
  проект (фикстура маленькая и написана здесь же), что сгенерированный B
  согласован, и что статус выше `tested` заслужен. Это выясняется на первом
  реальном прогоне, и расхождения идут в журнал, а не замалчиваются.
- **Ключевое ограничение:** конвейер выводит из кода **гварды, эффекты и
  структуру**. Цели безопасности он не выдумывает: он предлагает кандидатов,
  а утверждает человек. Автоматического `approved` не существует.

## 1. Что нужно на машине

| Компонент | Обязателен | Зачем |
|---|---|---|
| Python ≥ 3.11 | да | все инструменты конвейера (stdlib + PyYAML) |
| PyYAML | да | YAML-артефакты (`primitives.yaml`, `decisions.yaml`), чтение схем; тот же пакет нужен `make verify` |
| git | да | коммит цели, dirty-флаг, история артефактов |
| make, bash | да | входные точки |
| ssh-keygen | для `make verify` | проверка подписанных якорей |
| rustc / cargo | нет | конвейер **не компилирует** цель, только читает `.rs` |
| probcli (ProB) | нет | наличие проверяется и записывается в `env.json`; V0 не вызывает его и не даёт `proven` |
| сеть | нет | всё локально; ничего не скачивается |

Конвейер сам пакеты не ставит. PyYAML должен уже стоять — его требует
`make verify`, поэтому в развёрнутом репозитории он есть. Если его нет,
`model-doctor` выходит с кодом 2 и печатает команду установки.

Проверка окружения:

```bash
python3 -V                 # ≥ 3.11
python3 -c 'import yaml'   # нужен и конвейеру, и общим линтерам
git --version
make --version
```

## 2. Где что лежит

| Что | Где |
|---|---|
| Все шаги конвейера | `tools/model_*.py` |
| Общая схема, якоря, хэши | `tools/model_primitives.py` |
| JSON-схемы артефактов | `spec/models/*.schema.json` |
| Фикстура для самопроверки | `spec/fixtures/rust-tiny/` |
| Эта инструкция | `docs/conveyor-agent.md` |
| Общие гейты репозитория | `Makefile`, `docs/onboarding.md` |
| Статический анализ (не часть конвейера) | `spec/static-analysis/`, `tools/sarif_evidence.py` |

Артефакты прогона по умолчанию — `<target>/model/`. Флаг `--out` выносит их
наружу. В артефактах **нет исходного кода**: якорь — это
`{path, start, end, sha256 фрагмента}`. Поэтому `model/` можно коммитить.

## 3. Куда агент складывает журнал и метрики

Пока проекты локальные, всё возвращается в один каталог на машине агента, и мы
забираем его оттуда. Путь не зашит в инструменты — он приходит из переменной
`MODEL_HANDOFF_DIR`.

```bash
# 1. Куда класть. По умолчанию — каталог загрузок этой машины.
export MODEL_HANDOFF_DIR="$(xdg-user-dir DOWNLOAD 2>/dev/null || echo "$HOME/Downloads")"

# 2. Папка проекта: имя = имя каталога цели.
export PROJECT="$(basename "$TARGET")"
mkdir -p "$MODEL_HANDOFF_DIR/$PROJECT"
```

Раскладка, которую мы ожидаем найти:

```
<MODEL_HANDOFF_DIR>/<project>/
  README.txt                  # одна страница: что это и как читать
  handoff.json                # манифест: версии, хэши, счётчики, открытые вопросы
  JOURNAL.md                  # журнал агента, дописывается, не переписывается
  journal/
    2026-11-08T20-31-12Z/
      events.jsonl            # события инструмента, append-only
      console.log             # сырой вывод команд этого прогона
  metrics/
    metrics.jsonl             # одна строка на запуск шага
    summary.md                # сводка, собранная из metrics.jsonl
  artifacts/
    env.json                  # версии, ОС, наличие rustc/probcli, commit цели
    inventory.json            # что нашёл scan: файлы, структуры, функции
    bounds.yaml               # если задан; иначе файла нет
    primitives.yaml
    decisions.yaml
    review.md
    review-index.json         # required-очередь: id, путь, линия, риск-тир
    review/                   # per-area detail: операции и их assert-инварианты
    MODEL.md
    generated/model.json
    generated/model.sys
    checks/results.json
  target.json                 # путь, commit, dirty, число файлов
```

Правила:

- **Одна папка на проект**, попытки внутри (`journal/<ts>/`), а не папка на
  попытку. История должна быть видна целиком.
- **Ничего не удаляется.** Неудачный прогон остаётся: он и есть материал для
  починки системы.
- **Ничего не уходит в сеть** и не публикуется в GitHub.
- Если `MODEL_HANDOFF_DIR` не задан, `model-handoff` пишет в
  `<target>/.model-handoff/` и предупреждает, что каталог не тот.

## 4. Пошаговый прогон

Порядок обязателен: каждый шаг читает выход предыдущего.

### Шаг 0. Подготовить каталог

Передача локальная: каталог копируется целиком, вместе с неотслеживаемыми
файлами. `git clone`, `git archive` и `git worktree` берут только tracked
файлы и оставят конвейер за бортом. `git clean -fd` на принимающей стороне
удалит его так же.

```bash
rsync -a /путь/к/dev-sec-skills/ ~/dev-sec-skills/
cd ~/dev-sec-skills
make model-doctor
```

Если каталог всё-таки получен клоном, конвейер должен быть в коммите:
проверьте, что `tools/model_doctor.py` и `docs/conveyor-agent.md` существуют,
прежде чем идти дальше.

`model-doctor` копирует `spec/fixtures/rust-tiny/` во временный каталог и
прогоняет все шаги через настоящий командный интерфейс, как это делал бы агент:
init → scan → extract → review → (решения из фикстурного oracle) → gen → check →
report → handoff. Затем проверяет артефакты по схемам, валидирует `handoff.json`
офлайн, проверяет `bounds.yaml` и запускает негативные тесты.

Коды: 0 — установка рабочая; 1 — конкретная проверка не прошла, в выводе
написано какая; 2 — окружение не готово (нет PyYAML, git, схемы, фикстуры)
или инструмент упал на внутренней ошибке.
Каталог прогона сохраняется при ошибке, `--keep` сохраняет его и при успехе;
`make model-doctor KEEP=1`.

Doctor проверяет фикстуру, а не ваш проект. Он не доказывает, что лексер
понимает ваш Rust.

### Шаг 1. Зафиксировать цель

```bash
export TARGET=/путь/к/rust-проекту
git -C "$TARGET" rev-parse HEAD      # если это git-репозиторий
git -C "$TARGET" status --porcelain  # должно быть пусто, иначе dirty=true
```

Dirty-цель допустима, но в `handoff.json` она будет помечена, и якоря
относятся к рабочему дереву, а не к коммиту.

### Шаг 2. Создать рабочий каталог

```bash
make model-init TARGET="$TARGET"
```

Создаёт `<target>/model/` с `bounds.yaml.example` и `JOURNAL.md`. Если цель
нельзя трогать:

```bash
make model-init TARGET="$TARGET" MODEL_OUT="$MODEL_HANDOFF_DIR/$PROJECT/artifacts"
```

`MODEL_OUT` переносит **все** артефакты, включая `runs/`; дальше его нужно
передавать каждому шагу, иначе следующий шаг будет искать файлы в
`<target>/model/`.

### Шаг 3. Инвентарь

```bash
make model-scan TARGET="$TARGET"
```

Пишет `model/inventory.json`: файлы `.rs`, строки, `struct`/`enum`/`impl`,
точки входа `pub`, `&mut self`-методы, `unsafe`/`extern`, неразобранные
файлы. Неразобранный файл — это `unmapped` с причиной, а не пропуск.

### Шаг 4. Извлечение примитивов

```bash
make model-extract TARGET="$TARGET"
```

Пишет `model/primitives.yaml` — каждый примитив со статусом `proposed`, якорем
и полем `unmapped[]` для того, что не удалось разобрать. Файл перезаписывается
целиком: это выход инструмента. Решения человека живут отдельно, в
`decisions.yaml`, поэтому повторное извлечение их не теряет.

### Шаг 5. Предъявление человеку

```bash
make model-review TARGET="$TARGET"
```

Пишет `model/review.md` — сводку и риск-очередь (сверка очереди с тирами
внутри: required = tiered operations + entities + state + doc invariants,
разница посчитана, а не спрятана); `model/review/` — per-area
детали (каждая требующая решения операция со своими гвардами, эффектами и
assert-инвариантами); `model/review-index.json` — машиночитаемый список
required-примитивов (id, путь, линия, риск-тир, решение); и
`model/decisions.yaml` — по одной записи на каждый **required**-примитив:
`entities`, `state`, операции, которые публичны или `&mut self`, и doc-инварианты.
У новой записи `decision: null`. Уже принятые решения сохраняются по `id`;
если `id` исчез из кода, решённая запись остаётся в конце файла, а `review`
печатает предупреждение об orphan.

Чего в `decisions.yaml` нет — и почему:

- **тестовый код** (`tests/`, `*_tests.rs`, `benches/`, `examples/`) — вне
  очереди по умолчанию; `--include-tests` возвращает его в `review.md`, но
  приватные тестовые функции всё равно не required;
- **приватные операции без эффектов и без `&mut self`** — за них отвечают
  вызывающие; они попадают в бакет `not_required` и в `review.md` видны без
  колонки решения;
- **assert-инварианты** — они следуют за своей операцией: утвердив операцию,
  человек утвердил и её `assert!`, что фиксируется как групповое решение
  (`decided_by` в `generated/model.json`).

На первом реальном прогоне это сократило очередь с 59 046 записей и
295-тысячного файла до ~10,5 тыс. required-решений.

**Дальше работает человек.** Он ставит в `decisions.yaml`:

```yaml
- id: O-Permissions-grant
  decision: approved        # approved | rejected | deferred | null
  by: "имя"
  at: "2026-11-08"
  note: "гвард действительно обязателен: без него роль можно выдать себе"
```

Для `&mut self`-операции без синтаксического гварда нужна либо правка кода,
либо явное:

```yaml
- id: O-Permissions-reset
  decision: approved
  no_guard_ok: true
  note: "вызывающий держит write-lock; проверка в Permissions::lock"
```

Правила:

- агент **не** заполняет `decision` за человека;
- `rejected` и `deferred` обязаны иметь `note`;
- `no_guard_ok: true` без `note` — ошибка `coverage`, а не тихий пропуск;
- если человек не отвечает, шаг 6 не запускается — это блокер, и он идёт в
  журнал.

### Шаг 6. Генерация модели

```bash
make model-gen TARGET="$TARGET"
```

Читает **только `approved`**. Пишет `model/generated/model.json` (машиночитаемая
модель) и `model/generated/model.sys` (каркас B). `rejected`/`deferred` и
`proposed` в модель не попадают; их `id` перечислены в `excluded`.

`model.sys` — именно каркас. Гвард и эффект, выражение которого инструмент не
перевёл, остаются комментарием; `String` и незнакомые типы не угадываются, а
попадают в `unknown_types`. Считать этот файл доказанным нельзя, и он сам об
этом пишет в заголовке.

### Шаг 7. Проверка

```bash
make model-check TARGET="$TARGET" MODEL_ENV=offline
```

`MODEL_ENV` (или `--environment offline|ci|full-local` при прямом вызове
инструмента) обязателен: окруженческий scope делает фейл классифицируемым.
«Фейлит у меня в offline-сборке без `CRAFT_I18N_DIR`» и «фейлит в CI» —
разные находки: первое различило баг PR и артефакт машины в Iteration 3.
Без значения шаг падает с ошибкой, а не пишет пустой scope.

Пишет `model/checks/results.json` (включая `environment`) и печатает таблицу
проверок. Что проверяется:

| Проверка | Что ловит | Блокирует |
|---|---|---|
| `anchor` | фрагмент кода изменился или файл исчез → `stale`/`missing` | да |
| `coverage` | публичная точка входа без решения; `&mut self` без гварда и без `no_guard_ok`; `no_guard_ok` без `note` | да |
| `vacuity` | гвард `false` или противоречивые сравнения (`x == 1 && x == 2`) | да |
| `dead_state` | поле, которое никто не пишет или никто не читает | нет, `warn` |
| `theorem` | инвариант-тавтология (блокирует); инвариант, чей scope не трогает названные поля (предупреждение) | тавтология — да |

`bounds.yaml` **не** поднимает статус в V0. Файл читается, проверяется на
наличие `rationale` и записывается в `checks/results.json` как
`bounds.declared: true, bounds.enumerated: false`, потому что перебора за ним
пока нет. `model-checked` появится только вместе с реальным ограниченным
перебором. Числа выбирает агент под свой проект и обосновывает:

```yaml
bounds:
  max_instances: 3
  max_depth: 4
  max_states: 10000
  rationale: "три пользователя и три роли покрывают все ветки SoD; глубже — взрыв состояний"
```

### Шаг 8. Отчёт

```bash
make model-report TARGET="$TARGET"
```

Собирает `model/MODEL.md` из утверждённого каталога, результатов проверок и
реестра свидетельств. Каждая строка отчёта ссылается на якорь или на артефакт.
Статус (`open` / `tested`) выводится из артефактов, а не вписывается рукой;
в V0 выше `tested` он не поднимается.

### Шаг 9. Сборка handoff

```bash
make model-handoff TARGET="$TARGET" MODEL_HANDOFF="$MODEL_HANDOFF_DIR/$PROJECT"
```

Без `MODEL_HANDOFF` путь берётся из `MODEL_HANDOFF_DIR` (плюс имя проекта), а
если нет и её — папка создаётся внутри цели, и инструмент предупреждает, что
это не тот каталог.

Копирует артефакты, журнал и метрики в папку проекта, пишет `handoff.json` и
`README.txt`, проверяет `handoff.json` по схеме и пересчитывает хэши файлов.
В манифесте: версия инструментов, окружение, коммит цели, dirty, хэши всех
артефактов, счётчики, метрики, список открытых вопросов и ограничения.
Отсутствие `JOURNAL.md` — ошибка, а не предупреждение: папка не собирается.

Проверить уже собранную папку, не запуская шагов:

```bash
make model-validate MODEL_HANDOFF="$MODEL_HANDOFF_DIR/$PROJECT"
```

Валидатор перечитывает `handoff.json`, сверяет его со схемой и пересчитывает
хэш каждого файла. Он не проверяет, что артефакты внутри верны — только что
они те, на которые ссылается манифест.

### Шаг 10. Повтор

Правки в `decisions.yaml` или в коде цели → снова шаги 4–9. `metrics.jsonl`
пересобирается из всех `journal/*/events.jsonl`; старые каталоги прогонов не
перезаписываются.

`run_id` по умолчанию — текущая секунда UTC, поэтому шаги, запущенные в одну
секунду, делят один каталог `journal/<run_id>/`, а растянутый прогон даёт
несколько. Порядок внутри файла задаёт `seq`, а не имя каталога. Чтобы
склеить намеренно длинную итерацию в один каталог, задайте метку:

```bash
export MODEL_RUN_ID="$(date -u +%Y-%m-%dT%H-%M-%SZ)-attempt2"
```

### Протокол прогонов тестов цели (run-protocol)

Обе главные ловушки 2026-11-13 (stale-артефакт, English-only билд) — ловушки
прогонов, не ревью: точность ревью и так 95%, а верификация без протокола —
лотерея. Чеклист обязателен перед каждым прогоном тестов цели:

1. **touch исходников перед КАЖДЫМ прогоном** в общем `CARGO_TARGET_DIR`.
   Одинаковые metadata-хэши дают всем worktree один артефакт и один
   fingerprint: прогон worktree A после компиляции worktree B запускает бинарь
   B. Точный триггер mtime-совпадения не установлен — проверяй каждый раз.
2. **strings по бинарю после сборки**: `strings <test-бинарь> | grep <имя
   нового теста>`. Ноль вхождений — прогон фиктивен: «зелёных» тестов, которых
   нет в бинаре, не существует (ловля через `strings` → `comm` → `touch`).
3. **Контракт окружения**: `CRAFT_I18N_DIR` (checkout репозитория каталогов,
   не craft-libs) для ui-egui it-тестов с языковыми зависимостями — без него
   билд English-only и языковые тесты фейлятся фиктивно; `TMPDIR`;
   `CARGO_TARGET_DIR`.
4. **Подозрительный фейл — бейзлайн на чистом upstream/main.** Те же фейлы на
   чистом main в offline-сборке — артефакт окружения, не баг PR (в CI
   `CRAFT_I18N_REQUIRED=1` — ошибка вместо warning, там таких ложных нет).
   Окружение каждого чека записывается обязательно: `model-check
   --environment offline|ci|full-local`.
5. **Перед пушем `clippy --workspace --all-targets -D warnings`.** Union
   use-списков при ребейзе теряет импорты (`format_date_in`, #5676); fmt не
   ловит.

### Роль runner-агента

Прогонам нужна сборка, а конвейеру — журналирование. Отдельная роль
runner-агента:

- разрешено: сборка и прогоны тестов цели в **выделенном worktree** (свой
  checkout, отдельный `CARGO_TARGET_DIR` или touch перед каждым прогоном);
- обязателен протокол прогонов выше; каждый прогон — в журнал конвейера
  (`JOURNAL.md` + `events.jsonl`), иначе прогон вне конвейера и его «зелёный»
  — не свидетельство;
- запрещено: пуш без clippy (пункт 5), вердикт о PR без записанного окружения
  прогона.

Тогда прогоны попадают в конвейер как остальные шаги, а не остаются только в
журнале отдельного агента.

## 5. Журнал: два канала, оба обязательны

### Канал 1 — `events.jsonl` (пишет инструмент)

Одна строка на шаг, append-only, никогда не редактируется задним числом:

```json
{"ts":"2026-11-08T20:31:12.421Z","run_id":"2026-11-08T20-31-12Z","seq":3,
 "step":"extract","argv":["--target","/home/u/proj"],
 "cmd":"python3 tools/model_extract.py --target /home/u/proj",
 "cwd":"/home/u/dev-sec-skills","target":"/home/u/proj",
 "target_commit":"a1b2c3d","target_dirty":false,
 "exit":0,"duration_ms":812,
 "inputs":[{"path":"src/lib.rs","sha256":"…"}],
 "outputs":[{"path":"model/primitives.yaml","sha256":"…"}],
 "counts":{"primitives":12,"unmapped":3},"status":"ok","error":null}
```

Упавший шаг тоже пишет строку, с `exit≠0`, `status:"error"` и текстом ошибки.
Строка без ошибки у упавшего шага — дефект инструмента, его надо вернуть нам.

### Канал 2 — `JOURNAL.md` (пишет агент)

Шаблон на каждую итерацию:

```markdown
## Итерация 2 — 2026-11-08T20:31Z

### Намерение
Что собирался получить и почему именно так.

### Команды
Точные команды, без сокращений.

### Факт
Что реально получилось: числа, пути, коды возврата.

### Расхождение с ожиданием
Где результат не совпал с намерением. Это самое ценное место.

### Решения
Что выбрал и по какой причине. Особенно: какие `rejected`/`no_guard_ok`
и почему.

### Блокеры и вопросы
Что не смог без человека.

### Что предлагаю изменить в инструменте
Конкретно: шаг, вход, ожидаемое поведение.
```

Правила журнала:

- один раздел на итерацию, дописывается снизу;
- неудача описывается так же подробно, как удача;
- «всё работает» без чисел и путей — не запись;
- если правил `decisions.yaml`, укажи, что именно и по чьему решению.

## 6. Метрики

`metrics/metrics.jsonl` — одна JSON-строка на запуск шага. Поля строки:

| Поле | Смысл |
|---|---|
| `ts`, `run_id`, `step`, `exit`, `status`, `duration_ms` | когда, что и с каким кодом запускалось |
| `target_commit`, `target_dirty` | к какому состоянию цели относятся числа |
| `counts` | счётчики этого шага (`files`, `fns`, `guards`, `stale`, …) |
| `error` | текст ошибки у упавшего шага, иначе `null` |

`summary.md` целиком выводится из этих строк, ничего не вписывается рукой:

| Величина | Как считается |
|---|---|
| покрытие гвардами | `&mut self`-операции, вошедшие в модель, у которых есть гвард **или** `no_guard_ok` с `note`, ÷ все такие операции |
| доля unmapped | `unmapped` ÷ (`entities`+`state`+`operations`+`invariants`+`unmapped`) |
| stale-доля | `stale` ÷ `anchors` |
| вакуумность | `vacuity_hits` на 100 инвариантов |
| доля утверждённых | `approved` ÷ все принятые решения |
| сбои | число шагов с `exit≠0` (счётчик, не доля) |
| время шага | медиана `duration_ms` по всем строкам и отдельно по шагам |
| шаги | число строк и `by_step` |
| исключения | `excluded_steps: ["handoff"]` — шаг не может измерить сам себя |

`handoff` пишет своё событие уже после того, как числа собраны, поэтому в
метриках текущего прогона его нет. В следующем прогоне его событие попадёт в
выборку — это видно по `by_step`.

Эти числа нужны не для отчёта, а для починки: рост доли `unmapped` после
правки лексера означает регрессию; `vacuity_hits > 0` при `tested` означает,
что «доказано» относится к пустому множеству; падение покрытия гвардами после
`no_guard_ok` без `note` показывает, где ослабили модель.

Если `model-handoff` недоступен, папку можно собрать вручную, но `handoff.json`
придётся писать самому, и валидатор его не примет как манифест:

```bash
cp -r "$TARGET/model/." "$MODEL_HANDOFF_DIR/$PROJECT/artifacts/"
cp -r "$TARGET/model/runs/." "$MODEL_HANDOFF_DIR/$PROJECT/journal/"
cp "$TARGET/model/JOURNAL.md" "$MODEL_HANDOFF_DIR/$PROJECT/"
```

Сначала сообщите о поломке `model-handoff` и приложите журнал; ручная сборка —
временная мера, а не замена шагу.

## 7. Чего агенту делать нельзя

1. Утверждать примитивы за человека.
2. Править `primitives.yaml` руками: источник — `decisions.yaml`.
3. Ставить `no_guard_ok` без причины, которую можно проверить.
4. Задавать `bounds.yaml` числами «на глаз» без `rationale`.
5. Копировать исходный код в артефакты.
6. Менять файлы цели, кроме `<target>/model/`.
7. Повышать статус вручную. V0 вообще не выдаёт `model-checked`: даже с
   `bounds.yaml` файл записывается как `enumerated: false`. `proven` требует
   Rodin/ProB и в V0 не достигается.
8. Переписывать прошлые записи журнала.
9. Публиковать модель или артефакты в GitHub.
10. Молча пропускать файл, который не разобрал лексер.
11. Публиковать ссылку на символ, строку или цитату кода без grep-проверки
    перед публикацией. Каждая цитата кода = grep: символ, строка или
    `файл:строка` в черновике комментария проверяются поиском по цели до
    публикации. Неточность `break_mark` в Iteration 3 была бы поймана
    суб-агентом самому себе этим правилом.

## 8. Типовые сбои

| Симптом | Причина | Что делать |
|---|---|---|
| `lex: unterminated block comment at L:C` или `unbalanced` | лексер не разобрал файл | файл попадает в `unmapped` с якорем и причиной `lex-error`; записать в журнал и вернуть нам файл целиком |
| `anchor fail … snippet changed` | код изменился после извлечения | перезапустить `model-extract`, не подменять хэш |
| `check: bounds.yaml: every bound needs a rationale` | числа без причины | дописать `rationale` или убрать файл; статус всё равно не поднимается |
| шаг упал на внутренней ошибке, exit 2 | исключение вне ожидаемого | traceback в `runs/<ts>/console.log`, событие в `events.jsonl` со `status: error`; вернуть нам оба файла целиком |
| `handoff: SameFileError` или дубль `runs/` | `MODEL_OUT` совпал с `<handoff>/artifacts` | исправлено в V0.1: копия пропускается, `runs` не дублируются |
| `coverage fail … &mut self without a guard` | решение без `no_guard_ok` | либо гвард в коде, либо `no_guard_ok: true` с `note`, где проверка |
| `coverage fail … no_guard_ok without a note` | причина не названа | написать проверяемую причину или убрать флаг |
| `vacuity fail … condition is literally false` | недостижимый гвард | чинить код или модель; «доказательство» об этом гварде пустое |
| `gen: nothing is approved in decisions.yaml` | человек ещё не решил | это блокер, а не повод утвердить самому |
| `review: decisions for ids that no longer exist` | код переименован | решить, удалить ли orphan-запись; `review` её сохраняет намеренно |
| `handoff: JOURNAL.md is missing` | агент не написал журнал | дописать `JOURNAL.md` и повторить шаг 9; папка без него не принимается |
| цель не git-репозиторий | нет коммита | `target_commit: null`, якоря относятся к рабочему дереву |
| файл не UTF-8 | лексер не читает | `unmapped` с причиной `non-utf8` |
| `model.sys` почти пуст | все выражения не переведены | это ожидаемо для V0; смотреть `unknown_types` и `excluded`, а не править `.sys` руками |
| прогон «зелёный», а новых тестов в бинаре нет | общий `CARGO_TARGET_DIR` между worktree: один артефакт и один fingerprint | touch исходников перед каждым прогоном + `strings <бинарь> \| grep <новый тест>`; см. протокол прогонов |
| `language must be one of auto, en` в offline-прогоне | `CRAFT_I18N_DIR` unset → билд English-only | выставить `CRAFT_I18N_DIR` на checkout каталогов (репозиторий каталогов, не craft-libs); это артефакт окружения, не баг PR |
| `clippy: unresolved import` после пуша | union use-списков при ребейзе потерял импорт | `clippy --workspace --all-targets -D warnings` до пуша; fmt не ловит |

## 9. Что вернуть

Чек-лист перед отправкой:

- [ ] `<MODEL_HANDOFF_DIR>/<project>/` существует и непуста;
- [ ] `make model-validate MODEL_HANDOFF=...` печатает `handoff: valid`;
- [ ] `JOURNAL.md` содержит раздел на каждую итерацию, включая неудачные;
- [ ] `journal/<run_id>/events.jsonl` есть у каждого прогона;
- [ ] `metrics/metrics.jsonl` непуст, `summary.md` собран из него;
- [ ] `artifacts/env.json` фиксирует версии и наличие `rustc`/`probcli`;
- [ ] открытые вопросы перечислены в `handoff.json` и продублированы в
      последнем разделе `JOURNAL.md`;
- [ ] в папке нет исходного кода цели.

Вернуть нужно **путь к папке**, а не пересказ. Мы забираем её целиком и по ней
чиним систему.

## 10. Что этот документ не обещает

- Конвейер не выводит цели безопасности из кода. Он предлагает кандидатов,
  утверждает человек.
- B-модель и Event-B доказывают согласованность модели, а не соответствие
  коду. Привязка — якоря, и она остаётся выборочной.
- V0 не выдаёт `model-checked` и не вызывает ProB, поэтому `proven` в нём
  недостижим. Когда появится ограниченный перебор, он будет ограничен
  доменом из `bounds.yaml`.
- Первый прогон на реальном проекте почти наверняка даст `unmapped` и ложные
  гварды. Это ожидаемый результат, а не повод остановиться.
